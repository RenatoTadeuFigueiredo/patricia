# SEO Audit — patriciasenapsi.com.br

> **Date:** 2026-08-04 · **Status:** closed, every finding applied and verified in production
>
> **Scope covered:** `index.html`, `style.css`, `robots.txt`, `sitemap.xml`, live HTTP behavior,
> Core Web Vitals, Cloudflare zone config, the contact-form Worker, Search Console, and
> AI/LLM crawler access.
>
> **Method:** 7-dimension parallel audit with adversarial verification of every high/critical
> claim (37 confirmed, 3 refuted), plus live Lighthouse and a Chrome performance trace at
> mobile / Slow 4G / 4× CPU. Findings below are the confirmed set.
>
> **Scope gap, stated plainly:** the 7 dimensions were crawlability, content, schema, local,
> performance, accessibility and keywords. **None covered AI/LLM visibility.** That gap was
> found only because the owner asked about it afterwards, and it turned out to be the single
> largest blocker on the site (see AI crawlers below). A future audit of any site should treat
> AI crawler access as its own dimension.
>
> Companion doc: `docs/proximos-passos.md` — the roadmap and everything that needs a human.

## Tier 1 — Critical, fix first

### C-1. A stray `<img` destroys the hero `<picture>` — hero loads the 233 KB PNG instead of the 15 KB WebP

`index.html:347`

```html
            <img            <!-- ← this line -->
            <picture>
              <source srcset="fotos/patricia-sena-atendimento-hero.webp" type="image/webp">
```

The HTML5 tokenizer is in *before-attribute-name* state after `<img`, so it eats `<picture` as a bogus
attribute and closes the tag at the next `>`. Verified in the live DOM:

```js
document.querySelector('.hero-image').querySelectorAll('picture').length  // → 0
heroImg.currentSrc  // → ".../patricia-sena-atendimento-hero.png"   (233 KB, not the 15 KB .webp)
```

Two consequences:
1. **No `<picture>` element exists.** The `<source srcset="…webp">` has no `<picture>` parent, so browsers
   ignore it entirely. Every visitor downloads the **233 KB PNG instead of the 15 KB WebP — 15× larger.**
   The WebP conversion work logged in `proximos-passos.md` item 8 is dead for the hero image.
2. A phantom `<img <picture="">` renders at 0×260 px with no `alt`. That is the sole cause of the
   Lighthouse **SEO 92** and part of **Accessibility 91**.

**Fix:** delete line 347. One line.

*Verified after deploy:* `pictureCount` is now 1, `currentSrc` is the `.webp`, the phantom
`<img>` is gone. Note this saves 218 KB rather than LCP time on mobile — see the status
section above.

### C-2. `dislexia`, `Itaquera`, `Zona Leste` appear **nowhere** in visible body copy

`index.html` — all occurrences are in `<meta>` / `<title>` / JSON-LD (lines 9, 10, 29, 77, 101, 124, 169, 180, 191).

Grep of rendered text: `Itaquera` **0**, `Zona Leste` **0**, `dislexia` **0**, `reforço escolar` **0**,
`perto de mim` **0**. The visible page says only "São Paulo".

Meanwhile the JSON-LD asserts `areaServed: "São Paulo, SP - Zona Leste"` three times and the
`LocalBusiness.description` says "região de Itaquera - Zona Leste". Google ranks on rendered text;
`<meta name="keywords">` has been ignored since ~2009, and JSON-LD description strings drive rich-result
eligibility, not topical relevance. So the site claims a micro-region in machine-readable markup while
being **textually invisible** for the exact low-competition queries it could realistically win:
`psicopedagoga Itaquera`, `psicopedagoga zona leste`, `psicopedagoga dislexia`.

This is also a **content-parity** problem: Google's structured-data guidelines require markup to reflect
content visible on the page.

**Fix** — add visible copy in four places:
- Hero subtitle (`index.html:334-338`): name the region.
- `about-card` chip list (`425-432`): add `Dislexia e outros transtornos específicos de aprendizagem`.
- `info-banner` (`598-603`): replace bare "São Paulo" with the neighborhood list.
- FAQ answer at `629`: same.
- New short **"Área de atendimento"** block near the contact section listing real neighborhoods:
  Itaquera, José Bonifácio, Artur Alvim, Vila Matilde, Guaianases, Cidade Tiradentes, São Mateus,
  Ermelino Matarazzo.

⚠️ When you edit the FAQ text, **update the matching JSON-LD `FAQPage` answer** (`index.html:238`) in the
same commit, or the two diverge and you trade one parity problem for another.

## Tier 2 — High impact

### H-1. Title tag is 75 chars, truncates, and omits the differentiator

`index.html:8` — "Psicopedagoga em São Paulo | Patrícia Sena - Neuroeducação e Psicopedagogia" (75 chars).
Google's display budget (~570-600 px) cuts this around 55-60 chars for this character mix, so
"e Psicopedagogia" is lost — and it was redundant anyway (`psicopedagog-` already appears twice).

```html
<title>Psicopedagoga em São Paulo (Itaquera) | Patrícia Sena</title>   <!-- 53 chars -->
```

Mirror in `og:title` (`:28`) and `twitter:title` (`:38`).

### H-2. Meta description is 214 chars — the CTA never renders in the SERP

`index.html:9`. At the ~155-char cutoff it truncates to "…TDAH, dislexia, desate"; "Agende uma consulta!"
— the only call to action — is always cut.

```html
<meta name="description" content="Psicopedagoga em Itaquera, Zona Leste de São Paulo: avaliação e apoio para TDAH, dislexia e dificuldades de aprendizagem. Fale pelo WhatsApp.">
```
(138 chars.) Same fix for `og:description` (`:29`).

### H-3. Soft 404 — every nonexistent URL returns HTTP 200 with the full homepage

```
$ curl -sS -o /dev/null -w "%{http_code}\n" https://patriciasenapsi.com.br/nao-existe-xyz
200
```

Body is byte-identical to the homepage, **including the `canonical` pointing at `/`**. Same for
`/llms.txt`, `/qualquer-coisa`. Cloudflare Pages falls back to `index.html` with a 200 when no
`404.html` exists.

**Fix:** add a `404.html` at repo root. Cloudflare Pages auto-detects it and serves it with a genuine
HTTP 404 — no `_redirects`/`_routes.json` needed (and `_headers` **cannot** set status codes, so don't
try that route).

Include `<meta name="robots" content="noindex">` and **no** canonical tag on that page.

### H-4. No `rel=preload` for the LCP-critical resources

`grep preload index.html` → zero matches. The render delay is 96% of LCP (1340 of 1392 ms). The font is
only discovered after `style.css` parses; the hero image only at byte ~25 KB of a 48 KB document.

```html
<!-- before the <link rel="stylesheet"> at :66 -->
<link rel="preload" as="image" href="fotos/patricia-sena-atendimento-hero.webp" fetchpriority="high">
<link rel="preload" as="font" type="font/woff2" href="fonts/inter-latin.woff2" crossorigin>
```

**Do not preload `inter-latin-ext.woff2`.** Its `unicode-range` starts at U+0100; every pt-BR accented
character (ç ã õ á é í ó ú â ê) lives in U+00C0–00FF, covered by `inter-latin.woff2`. The 85 KB ext file
correctly never downloads for this content — preloading it would be 85 KB of pure waste.

### H-5. No `tel:` link anywhere — no click-to-call

`index.html:686` — `<span>(11) 94231-8641</span>` is inert text inside the WhatsApp anchor.
`grep 'tel:'` → 0 matches. The JSON-LD `telephone` (`:79`) has no on-page HTML backing it.

Don't nest a `tel:` inside the existing WhatsApp `<a>` (ambiguous nested tap target). Add a separate
secondary link in `.contact-card`, mirroring how the `mailto:` at `:698` already sits outside:

```html
<a href="tel:+5511942318641" class="contact-tel-cta">Ligar: (11) 94231-8641</a>
```

### H-6. All four images declare the wrong intrinsic aspect ratio, and none is responsive

Measured in the live DOM:

| image | declared | actual | rendered @390px |
|---|---|---|---|
| hero.png | 600×520 (1.154) | 407×612 (0.665) | 239×360 |
| livro-winnicott.webp | 500×500 (1.000) | **1065×1600** (0.666) | 213×320 |
| psicopedagoga | 500×440 (1.136) | — | 350×320 |
| consultorio | 500×280 (1.786) | — | 326×483 |

Two separate problems:
1. **Declared `width`/`height` don't match the files.** CLS happens to measure 0.00 only because CSS
   forces the real ratio — the attributes are doing nothing useful and are actively misleading.
   Correct them to the real pixel dimensions.
2. **No `srcset`/`sizes` on any `<source>`** (`:349, 378, 529, 664`) — only format switching. A phone
   renders `livro-winnicott` at 213×320 but downloads the full 1065×1600 file. Four unique photos; a
   one-time export of 400w/800w variants plus
   `sizes="(max-width: 768px) 100vw, 500px"` cuts ~20-40% of mobile image bytes.

### H-7. Form result message is invisible to screen readers

`index.html:775` — `<p id="form-message">` has no `role` / `aria-live`; JS at `:806,813` only sets
`textContent` and `style.color`. A screen-reader user submitting the site's **only** lead form gets no
announcement of success or failure. WCAG 4.1.3.

```html
<p id="form-message" role="status" aria-live="polite" aria-atomic="true" style="…"></p>
```

### H-8. WhatsApp float overlaps the form's submit button on mobile

`style.css:1580-1596` (`position:fixed; bottom:2rem; right:2rem; 60×60; z-index:1000`) vs the
full-width `.btn-full` submit at `index.html:771`. Verified by loading the live site at 375×667 and
scrolling the submit button into the float's zone — it overlaps. A mis-tap opens WhatsApp instead of
submitting.

The float is `position:fixed`, so it can collide at *some* scroll offset no matter how the card is
padded. The clean fix is to hide it while the contact section is on screen:

```js
const float = document.querySelector('.whatsapp-float');
new IntersectionObserver(([e]) => float.classList.toggle('is-hidden', e.isIntersecting),
  { threshold: 0.35 }).observe(document.getElementById('contato'));
```
plus `.whatsapp-float.is-hidden { opacity: 0; pointer-events: none; }`.

### H-9. `openingHoursSpecification` has zero visible counterpart

`index.html:107-112` claims Mon-Fri 08:00-18:00. `grep` for `08:00` / `18:00` / `horário` / `segunda`
outside the `<script>` block → 0 matches. Content-parity violation; a documented reason for Google to
distrust the `LocalBusiness` node — which matters the moment the Google Business Profile goes live.

Either publish the hours visibly in the contact section, **or** remove the property. Pick one; do not
leave it as-is.

### H-10. Four `aria-label`s override their own visible text (WCAG 2.5.3)

Flagged by Lighthouse `label-content-name-mismatch` — the agents' dimension sweep missed this one.

| element | visible text | `aria-label` |
|---|---|---|
| `a.logo` (`:286`) | "Patrícia Sena / Neuroeducação & Psicopedagogia" | "Patrícia Sena - Ir para o início" |
| `a.contact-whatsapp-cta` (`:680`) | "Fale pelo WhatsApp (11) 94231-8641" | "Enviar mensagem no WhatsApp" |
| mailto `a` (`:698`) | "patriciasenaeducar@gmail.com" | "Enviar e-mail" |
| Instagram `a` (`:709`) | "@patricia_sena_psicopedagoga" | "Perfil no Instagram" |

An accessible name must *contain* the visible label, so voice-control users saying what they see
("clique em Fale pelo WhatsApp") fail to activate the control. Either drop the `aria-label` (the visible
text is already a fine name) or extend it to include the visible string.

### H-11. WhatsApp CTA fails contrast: 4.13:1

Lighthouse measured `strong` inside `.contact-whatsapp-cta` — `#ffffff` on `#128c7e` at 15.2 px
normal weight = **4.13:1**, below the 4.5:1 AA threshold. Darken the green (`#0e7a6d` reaches ~5.1:1)
or bump the text to 600 weight ≥18.66 px.

## Tier 3 — Medium

- **`www` does not resolve at all.** `dig www.patriciasenapsi.com.br` → nothing; `curl` → "Could not
  resolve host". The apex is fine (`104.21.77.180`, http→https 301 works, `/index.html`→`/` 308 works).
  Anyone typing the `www` form — a very common default, and a form that appears in hand-typed
  directory listings — gets a hard DNS failure. Add a `www` CNAME + 301 to apex in the Cloudflare zone.
- **Asset `Cache-Control` is 4 hours.** `style.css`, both `.woff2`, and `fotos/*` all return
  `public, max-age=14400, must-revalidate` (Pages default). Add a root `_headers`:
  ```
  /fotos/*
    Cache-Control: public, max-age=31536000, immutable
  /fonts/*
    Cache-Control: public, max-age=31536000, immutable
  /style.css
    Cache-Control: public, max-age=604800
  ```
  Note: `style.css` has no content hash, so a long TTL there needs a cache-busting strategy first
  (`style.css?v=2`).
- **Remove the precise `geo` block** (`:89-93`). `-23.5396,-46.4539` is street-block precision in the
  Itaquera station area, published in machine-readable JSON-LD while the page tells humans the address is
  withheld until booking (`:629`). It buys nothing — Google will not emit a map pin from raw JSON-LD
  without a verified Business Profile — and it pre-creates a NAP conflict with the GBP you're about to
  make. Keep `address` at locality level, drop `geo`.
- **`Person` node is thin** (`:114-160`): no `sameAs`, no `image`, no `telephone`. For a solo
  practitioner giving advice about TDAH/dyslexia, the Person *is* the E-E-A-T entity. Add
  `"image": ".../fotos/patricia-sena-livro-winnicott.webp"` and
  `"sameAs": ["https://www.instagram.com/patricia_sena_psicopedagoga"]`.
- **No `WebPage` node, no `dateModified` anywhere** — zero freshness signal on a young page. Also, the
  `itemscope itemtype="https://schema.org/WebPage"` on `<html>` (`:2`) is **dead markup**: `grep itemprop`
  → 0 matches, so it declares a type with no properties and competes with the JSON-LD graph. Drop the
  microdata; add a real `WebPage` node with `isPartOf` / `about` / `dateModified`.
- **No honeypot on the lead form** (`:743-776`). The Worker endpoint is public in the HTML (`:797`).
  Add a hidden `name="website"` field and reject non-empty server-side (Worker lives outside this repo).
- **No `prefers-reduced-motion` block** in `style.css`. Hero runs `fade-in-up` unconditionally
  (`:302-307, 400-422`) and `scroll-behavior: smooth` is global (`:50-52`).
- **No JS fallback.** `<form id="contact-form">` (`:743`) has no `action`/`method`, so if the inline
  script fails the browser does a GET to `/` and silently discards everything typed. Add
  `action="https://formulario.renato-tadeu-figueiredo.workers.dev" method="POST"` and keep the
  `fetch` as progressive enhancement. Separately, the mobile nav is unreachable without JS
  (`.nav-list` is `opacity:0; pointer-events:none` until the JS toggle fires).
- **`reforço escolar SP` in meta keywords** (`:10`) contradicts the services described (`:460-519`) —
  the page explicitly is not tutoring. Drop it, or add a real FAQ entry drawing the distinction.
- **Missing "Área de atendimento" section.** No map, no directions, no neighborhood list anywhere,
  despite `areaServed` claiming Zona Leste. With no public street address a map embed is not useful —
  a crawlable text block does the geographic work instead. (Same edit as C-2.)

## Strategic: the one-page ceiling

1076 visible words on one URL cannot rank for a dozen distinct intents. Search results for every
commercial query checked are won by **dedicated single-query pages** (Doctoralia's own
`/avaliacao-psicopedagogica/sao-paulo`, Clínica Alcance's `/especialidade/psicopedagogia` for
"dislexia e tdah" in Tatuapé), not by homepage sections.

Recommended build order — service pillars **before** the blog, each targeting exactly one query, all
linked from nav + footer:

1. `/avaliacao-psicopedagogica` → `avaliação psicopedagógica zona leste são paulo` — highest commercial intent
2. `/neuroeducacao` → `neuroeducadora zona leste` — the differentiation wedge, least contested
3. `/psicopedagogia-tdah` → `psicopedagoga tdah zona leste sp`
4. `/psicopedagogia-dislexia` → `psicopedagoga dislexia são paulo`

Then `/blog/`, each post linking to its matching service page with a WhatsApp CTA, and each service page
linking back to 1-2 posts.
